# Tracker Mini Feature Plan

Use this file to track proposed and active feature work for the Polyend Tracker Mini Community Edition. Keep entries focused on the user need and Mini behavior. Mark proposals clearly; listing an idea here does not mean it has been accepted.

### Proposed: On-device pattern generation from human-readable `.pgen` files

- **User need:** Experiment with new or modified pattern-generation algorithms on the Tracker Mini without recompiling or reflashing firmware.
- **Expected Mini behavior:** Let the user browse human-readable `.pgen` files from `/PatternGenerators/`, choose an algorithm, edit its bounded parameters and seed, and run it as an explicit offline action from the Pattern Editor. Generate into a temporary copy with preview, accept, cancel, and undo/revert behavior using the Mini's D-pad, `interfaceButtonMiniMiddle`, and Shift combinations; do not require pads or a jog wheel. Accepted output becomes ordinary pattern data and plays back through the existing sequencer.
- **Scope:** Planning proposal for Tracker Mini. Define a small, versioned, human-readable pattern-generation language with parameters, bounded loops, conditions, deterministic random helpers, and commands for emitting notes, instruments, supported properties, and pattern effects. Load and interpret `.pgen` source files directly from the SD card; do not compile them into firmware or require a separate binary/compiled file format. Keep generation offline and outside audio-rate callbacks. Reuse existing pattern editing, undo, save, and SD text-file infrastructure where practical.
- **Constraints:** Use a bounded parser/interpreter with explicit limits for file size, execution steps, loop iterations, emitted events, and nesting; reject malformed or unsupported files safely with a useful error. Never perform SD access, allocation, or blocking work in audio-rate code. Preserve `.mt`, `.mtp`, `.pti`, `.pts`, and configuration compatibility by materializing accepted results into existing pattern structures without changing serialized enums or fields. Use deterministic seeds for reproducible output, keep generated patterns independent of the source file after acceptance, and review RAM, CPU, and UI responsiveness against the Mini memory map.
- **Validation plan:** Map `Sequencer::strPattern`, pattern editing/copy/undo behavior, project save/reload, file-browser integration, and Mini input/navigation paths before implementation. Define and test the `.pgen` grammar, versioning, parameter types, note/instrument/property/FX emission semantics, deterministic random behavior, target-pattern behavior, and all resource-limit failures. Verify that preview/cancel/undo leave the original pattern unchanged, accepted output saves and reloads as ordinary pattern data, and existing playback is unaffected. Build `make mini`; build all three targets if shared pattern code is changed; test the complete workflow and error handling on physical Mini hardware.
- **Clarification needed before implementation:** Decide the initial supported pattern fields and FX commands, whether generation may target multiple tracks or only the selected track, whether parameters are edited on-device or only supplied by file defaults, the maximum source-file size and execution budget, how source files are listed and selected in the Mini UI, and whether generated output should replace, merge with, or fill only empty steps in the target pattern.

### Proposed: Per-engine `.psyn` preset randomizer algorithms

- **User need:** Create varied synth sounds quickly while retaining human control over how randomness is applied, with reusable randomizer recipes that are understandable and shareable rather than opaque one-click randomization.
- **Expected Mini behavior:** For each supported `.psyn` synth engine, let the user browse human-readable randomizer definitions, choose an algorithm, set its seed and bounded parameters, preview the generated sound, and accept or cancel the result from the Mini's handheld UI using the D-pad, `interfaceButtonMiniMiddle`, and Shift combinations. The user may create and keep an arbitrary number of generation presets for any `.psyn` engine, subject to available storage and safe resource limits; each preset has a user-visible name and remains associated with its target engine and parameter schema.
- **Scope:** Planning proposal for Tracker Mini `.psyn` instruments, modeled on the proposed human-readable `.pgen` pattern-generation workflow. Define a small, versioned, human-readable format for randomizer algorithms and generation presets, including parameter ranges, weighted choices, constraints between parameters, deterministic random helpers, and engine-specific parameter addressing. Load and interpret definitions from the SD card without compiling them into firmware or requiring a separate binary format. Reuse existing synth parameter metadata, preset/file-browser, preview, undo, and save infrastructure where practical. Keep ordinary synth preset loading and existing projects unchanged when no randomizer preset is present.
- **Constraints:** Require an explicit target `.psyn` engine and validate definitions against that engine's parameter schema; reject unsupported, malformed, or incompatible files safely with a useful error. Bound file size, algorithm steps, nesting, parameter writes, and generated preset payloads; never allocate memory, access the SD card, or block in audio-rate callbacks. Use deterministic seeds for reproducible results, preserve parameter invariants and engine-specific safe ranges, and materialize accepted output as a normal synth preset independent of the source definition. Preserve `.psyn`, `.pti`, `.pts`, `.mt`, patch, and configuration compatibility; do not renumber serialized enums or move serialized fields without an explicit migration. Review RAM, flash, CPU, SD, and UI responsiveness against the Mini memory map.
- **Validation plan:** Map current `.psyn` engine registration, parameter metadata and schema/version handling, preset load/save, preview voice, file-browser, instrument serialization, and Mini navigation paths. Define and test the randomizer format, engine matching, parameter addressing, range/constraint behavior, weighted selection, deterministic seeds, arbitrary user preset creation/listing/deletion/rename, preview/cancel/undo, incompatible-engine handling, and all resource-limit failures. Verify accepted sounds save and reload as ordinary `.psyn` presets, old projects load identically, and preview cannot corrupt active voices. Build `make mini`; build all three targets if shared synth infrastructure changes; test the complete workflow and audible results on physical Mini hardware.
- **Clarification needed before implementation:** Decide whether algorithm definitions and user-created generation presets are stored as individual files, in per-engine folders, or in a project-local library; define the initial `.psyn` engines and parameter metadata contract; decide whether a generation preset stores only the algorithm and defaults or also a generated sound snapshot; define how users create and edit algorithms on-device versus editing files externally; choose naming, versioning, duplicate handling, and deletion behavior; and define storage/resource limits for an “arbitrary number” of presets.

### Proposed: Per-track polymetric length and pattern sync

- **User need:** Let each track cycle at its own step length while the pattern continues at its overall length, creating polymetric repetition without changing the pattern's shared timeline.
- **Expected Mini behavior:** Provide a per-track option to enable polymetric length, set that track's step length for the current pattern, and set how many repeats of that track cycle occur before it synchronizes to the pattern's step index. Expose the controls through the Mini's handheld UI (D-pad, `interfaceButtonMiniMiddle`, and Shift combinations); do not rely on pads or a jog wheel. Keep the option and values scoped to each track in each pattern.
- **Scope:** Planning proposal for Tracker Mini. Determine whether the eventual implementation belongs in shared sequencer code or needs device-specific UI; preserve existing pattern playback when the option is off.
- **Constraints:** Preserve project compatibility; do not reorder serialized enums or shift serialized fields without a compatible migration. Keep sequencing work bounded and real-time safe. Review memory use and existing pattern/track timing behavior before implementation. Document the user-facing control flow and compatibility behavior.
- **Validation plan:** Inspect the sequencer's pattern and track step-index handling; define expected sync behavior for lengths that divide and do not divide the overall pattern length; verify that disabled tracks retain current behavior and that the option/values survive save and reload. Build all three targets if the sequencer implementation is shared, and test the Mini interaction and playback on hardware.
- **Clarification needed before implementation:** Confirm what “how many pattern repetitions ... to wait to sync up to the pattern's step index” means: should the track keep looping its own length and then, after the chosen number of track cycles, jump to the step index corresponding to the global pattern position; or should the chosen number count full pattern repetitions before phase-resetting the track? Also confirm whether the track length counts steps (and its allowed range) and whether “sync” means resetting its playhead to the global pattern step, or merely aligning its next cycle boundary with the pattern boundary.

### Proposed: Barcode multi-playhead looper

- **User need:** Add a more organic, continuously evolving sample-handling mode in which one sample can be heard through several independently moving loop heads instead of a single conventional loop.
- **Expected Mini behavior:** Add a looper type named **Barcode** for the Mini's sample workflow. A selected sample is played by six independent playheads, mixed to the track output. Each head can have its own playback-rate choice (reference implementation: 1/8x, 1/4x, 1/2x, 1x, 2x, or 4x), reverse state, loop start and end points, amplitude, and pan. Slow per-head modulation may vary those parameters over time, with smoothed rate changes and click-safe loop-boundary handling. Provide all interaction through the Mini's handheld controls (D-pad, `interfaceButtonMiniMiddle`, and Shift combinations), with clear per-head selection and playhead feedback; do not rely on pads or a jog wheel.
- **Scope:** Planning proposal for Tracker Mini. Evaluate `external/barcode` as DSP reference code, adapting its `Barcode`, `BarcodeVoice`, `Playhead`, LFO, smoothing, and summing concepts to the firmware's sample playback and track-mixer architecture. Define whether Barcode is a new sample play mode, a variant of the proposed Looper type, or a separate track type, and whether one Barcode instance uses one source sample or multiple assigned samples. Keep existing Tracker and conventional loop behavior unchanged.
- **Constraints:** Preserve `.mt`, `.pti`, `.pts`, and configuration compatibility; do not reorder serialized enums or move serialized fields without a compatible migration. Keep sample loading, SD access, allocation, and parameter storage out of audio-rate callbacks; use the existing IMX streaming/cache architecture where possible and review RAM, CPU, SD bandwidth, and voice-count limits in the memory map. Ensure six playheads can sum without clipping and that reverse playback, wrapped start/end ranges, sample-rate conversion, loop transitions, and missing/streaming data remain real-time safe. Confirm licensing/attribution requirements before carrying over external reference code.
- **Validation plan:** Map the existing Mini sample play-mode, stream-manager, mixer, UI, and serialization paths. Prototype and measure six-head playback at all rate choices, forward/reverse operation, moving loop points, modulation smoothing, loop-boundary clicks, sample-rate mismatch, tempo changes if synchronization is supported, and sustained SD streaming without underruns. Verify parameter reset behavior when changing samples and deterministic save/reload behavior. Check audio CPU, RAM, flash, and SD bandwidth budgets; build `make mini` and all three targets if shared code is changed; test the handheld workflow and sustained playback on physical Mini hardware.
- **Clarification needed before implementation:** Decide whether Barcode should be a new type alongside Tracker/Rack/Looper or a mode within Looper; whether the six heads share one sample or can select separate samples; which parameters are user-editable versus generated by modulation; whether head rates are free-running or tempo-synced; how head state is triggered/reset by notes, pattern changes, stop/play, and sample changes; and how much per-head state should be serialized. Also confirm the intended UI layout and whether Barcode is Mini-only or should be available on Tracker+ through shared `PLATFORM_IMX` code.

### Proposed: Per-instrument filter and clipping chain with modulation

- **User need:** Give each instrument a compact, M8-inspired sound-shaping chain with multiple filter and clipping algorithms, reorderable processing, and the ability to modulate or automate the same parameters from the instrument and pattern workflows.
- **Expected Mini behavior:** On the selected instrument, provide a handheld-editable chain of filter and clipping stages. The user can choose an algorithm for each stage, change the stage order, and preview the result while playing the current pattern or instrument. Candidate filter algorithms include low-pass, high-pass, band-pass, band-stop, LP-to-HP, state-variable, and zero-delay-feedback low/high-pass modes; candidate clipping/waveshaping algorithms include hard clip, sine saturation, foldback, wrap, post-filter hard/soft clip, and bounded fold variants. Filter cutoff/resonance, drive/amount, algorithm, mix, and other agreed stage parameters must be available through the same modulation/automation model and through step FX, so a track can change them per step without duplicating the instrument.
- **Scope:** Planning proposal for the Tracker Mini, with shared `PLATFORM_IMX` DSP only where it is compatible with Tracker+. Define a bounded per-instrument chain representation and a stable parameter-addressing scheme before implementation. Reuse existing instrument envelopes/LFOs, pattern automation destinations, and step-FX infrastructure where practical. The M8 operation manual is the reference for its per-instrument filter modes, amplification/limiting modes, modulation slots, and step/table FX; arbitrary stage reordering is a proposed CE extension and must not be assumed to be an M8 behavior.
- **Constraints:** Preserve `.pti`, `.pts`, `.mt`, and configuration compatibility; do not reorder serialized enums or shift existing serialized fields. Prefer an extension/versioned representation or a migration path for new chain data. Keep all DSP state preallocated and audio-rate safe: no allocation, SD access, or blocking in render callbacks. Bound the number of stages and supported algorithms, smooth coefficient/drive changes, prevent denormals and runaway resonance, and define deterministic behavior for feedback, clipping, bypass, mono/stereo processing, and stage-order changes. Review CPU, flash, RAM, and per-voice/per-instrument state against the memory map; determine whether the feature is synth-only or also applies to sample, wavetable, and external-input instruments.
- **Validation plan:** Map current instrument signal paths, filter/limiter implementations, automation destinations, step-FX encoding, instrument serialization, and Mini parameter-screen navigation. Prototype each candidate algorithm and every permitted chain order; measure gain, resonance, aliasing, denormal, click, and CPU behavior at minimum/maximum settings and rapid automated changes. Verify that modulation, pattern step FX, note retrigger, preset changes, bypass, and save/reload address the same parameters consistently. Build `make mini`; build all three targets if shared code is changed; compare memory reports; test the Mini workflow and sustained audio on physical hardware.
- **Clarification needed before implementation:** Decide the maximum number of stages and whether a chain may contain repeated filter/clipping stages; which algorithms and parameters are in the first version; whether routing order is freely editable or selected from a small set of safe topologies; whether automation targets a stage by slot, algorithm, or stable parameter ID; how parameter conflicts between instrument modulation and step FX resolve; whether changing algorithm/order is allowed during playback; whether chains apply to all instrument types or only synth instruments; and whether the feature is Mini-only or shared with Tracker+.
- **Reference checked:** Dirtywave, [M8 Operation Manual](https://cdn.shopify.com/s/files/1/0455/0485/6229/files/m8_operation_manual_v20260421.pdf?v=1776791699), updated 2026-04-21; relevant sections are Instrument View, Instrument Modulation View, Instrument Pool View, and the Wavsynth/Macrosynth/Sampler filter and amplification parameter descriptions.

### Proposed: Synth instrument preset pool with preview and preset step FX

- **User need:** Let one synth track move between several related sounds during a song without allocating extra tracks or manually rewriting the instrument, while making it possible to audition and arrange those sounds directly on the Tracker Mini.
- **Expected Mini behavior:** A synth instrument owns a bounded pool of named preset slots containing complete parameter snapshots for that synth. From the Mini's handheld UI, the user can browse the pool, load or save a slot, preview the highlighted preset without changing the active sound, and commit a preset to the active instrument. A new pattern step FX selects a preset slot for the current synth track/instrument; the switch is applied at the defined step boundary, with optional quantized or immediate behavior, and the same instrument's envelopes, LFOs, filter/clipping chain, and automation destinations continue to operate on the selected preset. The UI must clearly show the active slot and provide safe fallback when a slot is empty, missing, or incompatible.
- **Scope:** Planning proposal for Tracker Mini synth instruments, using the existing `.psyn`/PolySynth parameter model and preset/file-browser infrastructure where possible. Define whether a pool is embedded in the instrument, stored as a separate pool file referenced by the instrument, or represented by existing preset files plus a compact index. Define the step-FX value encoding, pool capacity, naming, preview voice behavior, and whether a preset change affects only newly triggered notes or also updates currently sounding voices. Keep ordinary instrument assignment and existing projects unchanged when no pool or preset FX is present.
- **Constraints:** Preserve existing `.pti`, `.pts`, `.mt`, patch, and synth-preset compatibility; do not renumber serialized instrument or FX enums or shift existing fields without an explicit migration. Avoid copying large parameter/state blobs on the audio thread and do not perform SD I/O in audio-rate callbacks: load, validate, and prepare presets in the foreground/background, then publish a preallocated audio-safe snapshot at a musical boundary. Bound pool size and preset payloads to fit Mini storage/RAM and the synth plugin contract, define behavior when a plugin is unavailable or its parameter schema changes, and ensure preview cannot steal or corrupt song voices unexpectedly.
- **Validation plan:** Map current `.psyn` parameter metadata, synth preset load/save path, instrument serialization, file browser, voice allocation, pattern FX parser, and Mini navigation. Test browsing, preview, save/load, empty and incompatible slots, pool persistence, preset changes at note/step/phrase/pattern boundaries, rapid repeated changes, currently sounding voices, automation/modulation continuity, undo/cancel behavior, and missing files. Verify old projects load identically and new projects save/reload deterministically. Build `make mini`; build all three targets if shared synth or pattern code is changed; check memory/flash impact; test the complete workflow and audible switching on physical Mini hardware.
- **Clarification needed before implementation:** Choose the pool capacity and whether slots are per instrument or shared by synth type; decide whether a slot stores a full snapshot or references an external preset with overrides; define the step FX syntax/range and whether it selects an absolute slot or increments/decrements the current slot; decide when the change takes effect and what happens to sounding voices; define preview routing and whether preview may be heard while the song is playing; decide how plugin version/schema mismatches are handled; and confirm whether the pool should be available to all `.psyn` instruments or only selected built-in synths.
- **Reference checked:** Dirtywave, [M8 Operation Manual](https://cdn.shopify.com/s/files/1/0455/0485/6229/files/m8_operation_manual_v20260421.pdf?v=1776791699), updated 2026-04-21; relevant sections are Instrument View (load/save and preview), Instrument Modulation View, Instrument Pool View, Table View, and Instrument FX Commands.

### Proposed: Alternate sample, rack, and looper types for the first eight tracks

- **User need:** Let each of the first eight sample tracks work as a conventional tracker track, a one-shot rack, or a tempo-synced looper, while keeping its output on that track's mixer channel.
- **Expected Mini behavior:** The user can select one of three types for each of the first eight tracks: the existing Tracker type, Rack, or Looper. Preserve handheld operation through the D-pad, `interfaceButtonMiniMiddle`, and Shift combinations. Tracker retains current behavior. Rack provides 16 one-shot sounds, each with its own sequencer lane and per-sound level and pitch offset, plus attack/hold/release envelope controls. Looper provides 16 disk-streamed loops, each with per-sound level and pitch offset. The 16 sounds of the selected type are summed to the track's regular mixer channel.
- **Scope:** Planning proposal for Tracker Mini and the first eight sample tracks. Define how a selected track type interacts with existing instrument assignment, patterns, song playback, mixer controls, effects, and track settings before implementation. Keep tracks 9–16 and the three existing device targets' current behavior out of scope unless shared architecture requires compatible changes.
- **Constraints:** Preserve existing `.mt`, `.pti`, `.pts`, and configuration compatibility; do not reorder serialized enums or move serialized fields without an explicit migration. Keep SD reads and allocation out of audio-rate callbacks; use bounded background streaming and review cache/buffer needs against the memory map. Define loop time-stretching for host tempo from 90–180 BPM and power-of-two bar lengths, while allowing custom bar lengths. Preserve conventional Tracker playback when that type is selected. Document Mini controls and save/load behavior.
- **Validation plan:** Map the current first-eight-track playback, pattern, instrument, mixer, and file serialization paths. Specify type switching and persistence, Rack lane triggering and per-sound settings, and Looper disk streaming and time-stretch behavior, including tempo changes, custom bar lengths, loop boundaries, and SD underruns. Check CPU/RAM/SD bandwidth budgets and audio-thread safety; verify summed routing through the track mixer channel and unchanged Tracker playback. Build the Mini target and all three targets if shared code is changed; test controls, timing, save/reload, and sustained playback on physical Mini hardware.
- **Clarification needed before implementation:** Confirm whether type selection is per track or global across the first eight; whether choosing Rack/Looper replaces that track's existing instrument and pattern data or stores separate data alongside it; and what “a sequencer lane for each” means for Rack (16 lanes in the track's pattern, or another arrangement). For Looper, specify whether custom bar lengths may be fractional/non-integer, how pitch offset interacts with tempo lock and time-stretching, and whether loop lengths outside the stated power-of-two defaults are stretched to the entered bar count. Also decide whether the 90–180 BPM range is a limit on host tempo, source loop tempo, or both, and what behavior is expected outside that range.
