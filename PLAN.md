### Proposed: Per-track polymetric length and pattern sync

- **User need:** Let each track cycle at its own step length while the pattern continues at its overall length, creating polymetric repetition without changing the pattern's shared timeline.
- **Expected Mini behavior:** Provide a per-track option to enable polymetric length, set that track's step length for the current pattern, and set how many repeats of that track cycle occur before it synchronizes to the pattern's step index. Expose the controls through the Mini's handheld UI (D-pad, `interfaceButtonMiniMiddle`, and Shift combinations); do not rely on pads or a jog wheel. Keep the option and values scoped to each track in each pattern.
- **Scope:** Planning proposal for Tracker Mini. Determine whether the eventual implementation belongs in shared sequencer code or needs device-specific UI; preserve existing pattern playback when the option is off.
- **Constraints:** Preserve project compatibility; do not reorder serialized enums or shift serialized fields without a compatible migration. Keep sequencing work bounded and real-time safe. Review memory use and existing pattern/track timing behavior before implementation. Document the user-facing control flow and compatibility behavior.
- **Validation plan:** Inspect the sequencer's pattern and track step-index handling; define expected sync behavior for lengths that divide and do not divide the overall pattern length; verify that disabled tracks retain current behavior and that the option/values survive save and reload. Build all three targets if the sequencer implementation is shared, and test the Mini interaction and playback on hardware.
- **Clarification needed before implementation:** Confirm what “how many pattern repetitions ... to wait to sync up to the pattern's step index” means: should the track keep looping its own length and then, after the chosen number of track cycles, jump to the step index corresponding to the global pattern position; or should the chosen number count full pattern repetitions before phase-resetting the track? Also confirm whether the track length counts steps (and its allowed range) and whether “sync” means resetting its playhead to the global pattern step, or merely aligning its next cycle boundary with the pattern boundary.

### Proposed: Barcode multi-playhead looper

- **User need:** Add a more organic, continuously evolving sample-handling mode in which one sample can be heard through several independently moving loop heads instead of a single conventional loop.
- **Expected Mini behavior:** Add a looper type named **Barcode** for the Mini's sample workflow. A selected sample is played by six independent playheads, mixed to the track output. Each head can have its own playback-rate choice (reference implementation: 1/8x, 1/4x, 1/2x, 1x, 2x, or 4x), reverse state, loop start and end points, amplitude, and pan. Slow per-head modulation may vary those parameters over time, with smoothed rate changes and click-safe loop-boundary handling. Provide all interaction through the Mini's handheld controls (D-pad, `interfaceButtonMiniMiddle`, and Shift combinations), with clear per-head selection and playhead feedback; do not rely on pads or a jog wheel.
- **Scope:** Planning proposal for Tracker Mini. Evaluate `external/barcode` as DSP reference code, adapting its `Barcode`, `BarcodeVoice`, `Playhead`, LFO, smoothing, and summing concepts to the firmware's sample playback and track-mixer architecture. Define whether Barcode is a new sample play mode, a variant of the proposed Looper type, or a separate track type, and whether one Barcode instance uses one source sample or multiple assigned samples. Keep existing Tracker and conventional loop behavior unchanged.
- **Constraints:** Preserve `.mt`, `.pti`, `.pts`, and configuration compatibility; do not reorder serialized enums or move serialized fields without a compatible migration. Keep sample loading, SD access, allocation, and parameter storage out of audio-rate callbacks; use the existing IMX streaming/cache architecture where possible and review RAM, CPU, SD bandwidth, and voice-count limits in the memory map. Ensure six playheads can sum without clipping and that reverse playback, wrapped start/end ranges, sample-rate conversion, loop transitions, and missing/streaming data remain real-time safe. Confirm licensing/attribution requirements before carrying over external reference code.
- **Validation plan:** Map the existing Mini sample play-mode, stream-manager, mixer, UI, and serialization paths. Prototype and measure six-head playback at all rate choices, forward/reverse operation, moving loop points, modulation smoothing, loop-boundary clicks, sample-rate mismatch, tempo changes if synchronization is supported, and sustained SD streaming without underruns. Verify parameter reset behavior when changing samples and deterministic save/reload behavior. Check audio CPU, RAM, flash, and SD bandwidth budgets; build `make mini` and all three targets if shared code is changed; test the handheld workflow and sustained playback on physical Mini hardware.
- **Clarification needed before implementation:** Decide whether Barcode should be a new type alongside Tracker/Rack/Looper or a mode within Looper; whether the six heads share one sample or can select separate samples; which parameters are user-editable versus generated by modulation; whether head rates are free-running or tempo-synced; how head state is triggered/reset by notes, pattern changes, stop/play, and sample changes; and how much per-head state should be serialized. Also confirm the intended UI layout and whether Barcode is Mini-only or should be available on Tracker+ through shared `PLATFORM_IMX` code.

### Proposed: Alternate sample, rack, and looper types for the first eight tracks

- **User need:** Let each of the first eight sample tracks work as a conventional tracker track, a one-shot rack, or a tempo-synced looper, while keeping its output on that track's mixer channel.
- **Expected Mini behavior:** The user can select one of three types for each of the first eight tracks: the existing Tracker type, Rack, or Looper. Preserve handheld operation through the D-pad, `interfaceButtonMiniMiddle`, and Shift combinations. Tracker retains current behavior. Rack provides 16 one-shot sounds, each with its own sequencer lane and per-sound level and pitch offset, plus attack/hold/release envelope controls. Looper provides 16 disk-streamed loops, each with per-sound level and pitch offset. The 16 sounds of the selected type are summed to the track's regular mixer channel.
- **Scope:** Planning proposal for Tracker Mini and the first eight sample tracks. Define how a selected track type interacts with existing instrument assignment, patterns, song playback, mixer controls, effects, and track settings before implementation. Keep tracks 9–16 and the three existing device targets' current behavior out of scope unless shared architecture requires compatible changes.
- **Constraints:** Preserve existing `.mt`, `.pti`, `.pts`, and configuration compatibility; do not reorder serialized enums or move serialized fields without an explicit migration. Keep SD reads and allocation out of audio-rate callbacks; use bounded background streaming and review cache/buffer needs against the memory map. Define loop time-stretching for host tempo from 90–180 BPM and power-of-two bar lengths, while allowing custom bar lengths. Preserve conventional Tracker playback when that type is selected. Document Mini controls and save/load behavior.
- **Validation plan:** Map the current first-eight-track playback, pattern, instrument, mixer, and file serialization paths. Specify type switching and persistence, Rack lane triggering and per-sound settings, and Looper disk streaming and time-stretch behavior, including tempo changes, custom bar lengths, loop boundaries, and SD underruns. Check CPU/RAM/SD bandwidth budgets and audio-thread safety; verify summed routing through the track mixer channel and unchanged Tracker playback. Build the Mini target and all three targets if shared code is changed; test controls, timing, save/reload, and sustained playback on physical Mini hardware.
- **Clarification needed before implementation:** Confirm whether type selection is per track or global across the first eight; whether choosing Rack/Looper replaces that track's existing instrument and pattern data or stores separate data alongside it; and what “a sequencer lane for each” means for Rack (16 lanes in the track's pattern, or another arrangement). For Looper, specify whether custom bar lengths may be fractional/non-integer, how pitch offset interacts with tempo lock and time-stretching, and whether loop lengths outside the stated power-of-two defaults are stretched to the entered bar count. Also decide whether the 90–180 BPM range is a limit on host tempo, source loop tempo, or both, and what behavior is expected outside that range.
